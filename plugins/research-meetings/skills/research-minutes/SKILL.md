# research-minutes：研究會議的可溯源紀錄

## 研究會議和行政會議差在哪

內容紀律相同，差在記錄的對象與形式。

| | 行政會議（sinica-admin:meeting-minutes） | 研究會議（本 skill） |
|---|---|---|
| 記錄的核心 | 決議與權責 | 問題、理由、建議、結論狀態、誰去做什麼 |
| 形式 | 公文體、會議規範 13 款抬頭、標楷體 XeLaTeX → PDF | Markdown，放進研究 repo，GitHub 直接渲染 |
| 讀者 | 主席、各機關承辦人 | 合作者（含不在場的）、幾週後要寫方法段或回覆審稿的自己 |
| 下游用途 | 函復、書面報告 | 研究假設、分析計畫、方法段、作者協議 |
| 會後分析 | 補充說明（法規查證） | 補充說明（重跑程式、查套件文件），常常比會中說法更精確 |

## 內容紀律

**正本是 sinica-admin:meeting-minutes 的〈內容紀律〉。** 有安裝就先載入它，下列條目與它衝突時以它為準。
沒安裝時，下列八條是最低限度，不得省略：

1. **語意接近原文。** 原話說「可能」「我猜」「看看會不會」就照這個強度寫。多種寫法都有依據時，選最接近原話的，不選最精確的；精確化屬於補充說明。
2. **結論狀態用固定用語**，讓沒在場的人判得出能不能當結論引用：「有明確結論」（會中確認照此進行）／「建議，未定案」／「會中未有結論」。個別發言不寫成共識。
3. **歸屬要有證據。** 只有點名（「東台你先講」）、自述（「我是其中一個作者」）、或角色上只可能是某人時才寫姓名。轉錄的講者標籤（Speaker 1…N）不是身分：同一標籤常混進不同人，同一人也常被拆成兩個標籤。證據不足寫角色（「實驗室方」「統計諮詢方」）。
4. **聽不清的字不要補成通順的中文。** 先查來源（README、程式碼、簡報、名單）；查不到就寫粗粒度的說法，或不寫那個細節。
5. **不寫反應評價。** 「大家都同意」「討論熱烈」不寫；決議寫進狀態，發言寫進內容。
6. **不該流通的內容移入 HTML 註解，並寫明移除了什麼、為什麼**：對不在場且可被特定之第三人的評價、對機關動機的推測、對審查結果的預判、私人事務、離題閒談。用 `<!-- 【未列入】… 理由：… -->`，不要直接刪（刪掉的缺口日後會被當成漏記補回去）。
7. **製作方法不入正文。** 轉錄、校對、抽取的過程寫在 HTML 註解或溯源檔，不寫進看得到的內容。
8. **會後才知道的事放「補充說明」**，標明是紀錄者會後補充，並註明日期與依據（程式、輸出檔、文件版本）。討論事項的原文不改，只在該條狀態後加「（見補充說明一）」。

研究會議另加四條：

9. **方法建議寫成「誰建議、理由、條件」。** 「鄭澈建議先寫出研究假設」不能寫成「確定先寫研究假設」。紀錄者本人也是與會者（例如統計諮詢方自己記錄）時特別要守：自己的建議最容易被寫成結論。
10. **數字以程式碼、輸出、簡報為準。** 轉錄裡同一個數字有兩種說法（「百分之百」與「應該跟 α 一樣」）時，兩種都照原話記，或改寫成不含數字的陳述；不要挑一個寫。要確定的數值，到補充說明裡以重跑結果交代。
11. **合作與作者安排照原話記，未點名的人留〔待補〕。** 作者序、通訊作者、是否加入計畫都是會被事後引用的承諾，「他一定是第一作者」的「他」沒點名就不替他填。
12. **依使用者的寫作規範寫。** 中文紀錄不中英夾雜，統計術語用中文（檢定力、隨機截距、信賴區間），套件與軟體名保留原文（simr、SPSS、G*Power）；學者人名保留原文（Cohen）。

## 流程

### Step 0：建 task list

用 `TaskCreate` 為下列七步各建一個 task，完成即 `TaskUpdate → completed`。

### Step 1：素材、檔名、隱私邊界

- **檔名**：`<會議名>_<文件類型>_<YYYY-MM-DD>.<ext>`，例如 `推桿腦波研究第一次會議_會議紀錄_2026-10-07.md`。會議紀錄常以附件流通，檔名要自帶會議識別。用「紀錄」（名詞），不用「記錄」。
- **raw 與衍生物分開**，改名或建檔前先確認 `.gitignore`：

  | 檔案 | 性質 | 處置 |
  |---|---|---|
  | 錄音、逐字稿 `*.srt`、校對筆記 `*_校對筆記_*.md` | 第三方原話 | 不進 git remote |
  | 溯源驗證 `*_溯源驗證_*.jsonl`、抽取稿 | 含逐字摘錄 | 不進 git remote |
  | 會議紀錄 `.md` | 整理後的衍生產物 | 可 commit，但只進 private repo；commit 前查 `gh repo view --json isPrivate` |

  需要新 pattern 時，**先放寬 `.gitignore` 再改名**，改完逐檔跑 `git check-ignore -v` 確認。

### Step 2：取得逐字稿（只有錄音時）

依序交給 bestASR：`bestasr:context-ingest`（從 README、程式碼、名單蒸餾人名與術語）→ `bestasr:transcript`（帶 `--diarize`）→ `bestasr:srt-proofread`（用同一份 context 校對）。

- 有些 backend 不吃 context（`--explain` 會說），辨識時術語仍會錯，校對那一步才用得上 context，不要省。
- bestASR MCP 帶 diarize 在 v0.15.0 會 crash（PsychQuant/bestASR#194）。遇到時改用 repo 的 CLI build。

### Step 3：抽取（讀完整份逐字稿）

一小時的會議約 1800 個 cue。交給**一個** agent 完整讀完，產出可溯源的抽取稿（每點附 cue、時間碼、講者標籤、≤25 字短引文；議題標結論狀態；待辦只列明講的；列出講者標籤對照表與沒把握的地方）。提示詞見 `references/extraction-prompt.md`。抽取稿含逐字摘錄，放暫存目錄，不進 repo。

不要拆成多個 agent 平行讀：議題會跨段延續（同一個提問在第 30 分鐘提出、第 45 分鐘才回答），切段會把它們切斷。

### Step 4：撰寫紀錄

複製 `assets/template.md`，依內容紀律把抽取稿寫成紀錄。結構：抬頭 → 一、研究報告 → 二、討論事項（每題寫狀態）→ 三、待辦事項（依人分列）→ 四、補充說明（有才寫）。

### Step 5：溯源驗證

紀錄的每一點在 `<會議名>_溯源驗證_<日期>.jsonl` 各一行：

```json
{"id":"D2-4","section":"二/（二）","point":"轉述 AI：H1 與 H0 分不開","status":"attested","cues":"1305-1317","evidence":["H1跟H0幾乎分不開"],"note":""}
```

`status` 只有四種：`attested`（逐字稿錄到，evidence 必須逐字出現在 cues 範圍內）、`doc`（README、程式碼、名單等文件）、`inferred`（紀錄者的整理或推論）、`supplement`（會後補充）。後三種必須在 `note` 寫明來源。跑：

```bash
python3 -I ${CLAUDE_PLUGIN_ROOT}/skills/research-minutes/scripts/verify_provenance.py <校對版.srt> <溯源驗證.jsonl>
```

exit 0 才算完成。**不要憑讀過的印象寫 evidence**，從抽取稿或逐字稿複製。

### Step 6：文體檢查

```bash
python3 -I ${CLAUDE_PLUGIN_ROOT}/skills/research-minutes/scripts/check_style.py <會議紀錄.md> --allow-tai <含「台」的人名>
```

檢查破折號、強調用粗體、「台」、「會議記錄」、製作方法詞入正文（HTML 註解不算）。exit 0 才算完成。

### Step 7：交付

給使用者：紀錄路徑、每個討論事項的狀態、待辦清單，以及**需要他確認的事**：

- 所有〔待補〕（腳本會列出數量）；
- 所有 `inferred` 的點，尤其是講者歸屬；
- 轉錄裡互相矛盾、需要回頭核對程式輸出的數字；
- 移入 HTML 註解的段落（他可能想保留其中某些）。

commit 前先問；raw 檔一律不 commit。

## 失敗史

- **2026-10-07 第一次實作**（動作前腦波與推桿研究，59 分鐘、1877 cue）。
  - 講者標籤 Speaker 1 混進三個人：開場報告者、以第三人稱稱「鄭老師」的實驗室成員、統計諮詢方本人。照標籤歸屬會把實驗室成員的話寫成統計諮詢方說的。
  - 轉錄同一個檢定力結果有三種說法（「180」、「百分之百」、「跟 α 一樣」），會中沒有對起來。紀錄照原話記兩種，確切數值放補充說明的重跑結果。
  - 會中說「要再查」的事（simr 對自變項相關的預設），會後查得，放補充說明，並在待辦標「已於會後查得」。
